D01 — Execution authorization described as a Control Plane signed grant
Status: confirmed; repository correction pending.
Documentation:
- fred/docs/swift/platform/PLATFORM_RUNTIME_MAP.md:15 says all execution is
  authorized via ExecutionGrant from the Control Plane.
- Same file:27 assigns ExecutionGrant issuance to the Control Plane.
Code:
- fred/libs/fred-runtime/fred_runtime/app/agent_app.py:1901
  _authorize_execution_or_raise implements pod-side authorization.
- Same file:1981 and :2035 call the permission check using
  TeamPermission.CAN_USE_TEAM_AGENTS.
- Same file:2320, :5780 and :6019 explicitly describe the removal of signed grants.
- fred/apps/frontend/src/rework/core/hooks/useChatSse.ts around :1000 prepares
  execution then constructs runtime context including team_id; its adjacent
  comment explicitly says no signed grant.
- fred/apps/control-plane-backend/control_plane_backend/product/schemas.py:393
  ExecutionPreparation defines runtime URLs and context/settings, not a signed grant.
Current behavior: for managed execution with security/ReBAC enabled, the runtime
checks the authenticated user's team permission per request. Development modes
can bypass authorization; direct template execution has separate profile rules.
Correction: describe Control Plane preparation separately from runtime authorization;
remove claims that the Control Plane issues a signed execution grant.
Presentation impact: corrected in opening.html slides 2–3. Earlier index.html
three-slide design preview still contains the obsolete grant explanation and is
superseded for technical content; do not reuse its first slide unchanged.
