Fred Roadmap

Fred provides an open-source, collaborative and governed environment to work with data, use tools and carry out AI-assisted business workflows.

Current releases

Swift 3.x is the production release. Weaver 5.x is available to developers and remains incomplete. Kea 1.5 is obsolete.

Swift provides the runtime and SDK, document ingestion and retrieval, governed capabilities, evaluation and deployment tooling. Weaver consolidates these foundations around a common space model and clearer component responsibilities.

Scope. The priorities below describe the work guiding Weaver. They are not a delivery calendar or an inventory of completed features.

Architectural boundaries

Fred connects users, data and services within governed spaces. Domain services retain responsibility for business rules and records; applications provide the interfaces and process logic needed for a particular activity.

Governance
The Control Plane governs resource placement, lifecycle and access.
Knowledge processing
Dedicated services process documents and retrieve authorized content.
Agent execution
Agents use instructions and authorized tools to perform bounded tasks.
Business orchestration
Applications and domain services own process state, transitions and human decisions.

Approval of an agent's tool call and approval of a business milestone are separate operations, with distinct responsibilities and records.

Weaver priorities

Governed spaces

Consolidate ownership, access and resource lifecycle across organization, team, project and personal spaces. Documents, reusable instructions and assistant configurations need consistent rules for placement and use. A shared space does not make every conversation shared.

Prompts and skills

Build skill management on the Control Plane's space model, alongside prompts. Migrate the default skills out of fred-agents and align their packaging with the Agent Skills specification. Prompts express instructions; skills package procedures and supporting resources; capabilities expose executable operations. Skill instructions do not grant access rights. A skills marketplace can build on this foundation later.

Business applications

Provide practical capabilities for tasks such as working with complex spreadsheets and preparing presentations. Allow domain applications to combine these capabilities with their own interfaces and services, under the same access model. Users should be able to follow a business activity without managing its documents, instructions and progress across separate chats.

Reliable, resource-conscious execution

Use explicit workflows for predictable process rules and durable execution where work must survive interruptions. Introduce model reasoning where its contribution justifies its latency, cost and variability. Code execution is an optional capability subject to isolation, permissions and resource limits.

The same criteria apply to enterprise collaboration and smaller operational deployments: a clear interface, controlled resource use and traceable outcomes.

Under investigation: shared business progress

The working hypothesis is that collective work needs a small, explicit business state and a shared place to consolidate results. This state would record the current phase, references to accepted documents, decisions and transition history, independently of individual conversations.

For a bid team, several people and agents could prepare contributions in parallel. An authorized person would approve a gate against the consolidated deliverables; the application would record that decision and advance the process.

The design must address concurrent contributions, document revisions and approval authority. Where this state belongs, and which minimal contracts Fred should provide, remain open. This is not yet a completed Weaver feature.

Developer integration

Maintain a documented path from a local extension to evaluation, deployment and operation. Agents, tools, document processors and application interfaces should integrate through explicit contracts, with examples that demonstrate access boundaries as well as successful execution.

Distributed execution

Keep direct agent calls distinct from durable task delegation. Select the execution mechanism according to duration, recovery and tracking requirements. Distribution should serve a concrete integration need.

Platform guidance

Separate operator-editable guidance from platform-owned instructions, and reduce redundant model context. Authorization and business invariants must be enforced by services; prompt wording alone cannot guarantee them.

Evaluation criteria

Assess each addition against a concrete business activity: task completion and output quality, clarity of shared progress, correct access enforcement, recovery after interruption, latency and resource consumption. Extensions should integrate without modifying Fred's core.

Fred remains an open-source foundation for business assistance, consuming and connecting domain services. A general-purpose ERP and a universal business workflow engine are outside its scope.

An invitation to contribute

We welcome contributions from researchers, students and industrial teams. Exploring use cases on an open-source foundation, with real data and systems already in production, offers a rich setting for connecting research questions with operational experience.

Bring a use case, develop a capability, share an evaluation or document what worked and what did not. These contributions help shape both Fred and our understanding of AI-assisted work. Join us on GitHub to start the conversation.
