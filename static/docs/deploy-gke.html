Deploying Fred
on GKE

What a complete Fred deployment on Google Kubernetes Engine looks like — the components, the stores, and how you know it is actually correct, not just running.

Scope & audience

For operators and DevOps teams standing up Fred Swift 2.0 on GKE Autopilot. This page is the map: the shape of a deployment and its definition of "done". It deliberately does not reproduce the environment-specific runbook (hostnames, secrets, exact commands) — that lives with the Helm chart and stays in sync with it.

Two companion documents. The Architecture page covers component topology and the security perimeter; native Google Cloud Storage with Workload Identity (no service-account keys) has its own reference. This page is the operational overview that ties them together.

What "deployed" means — complete and correct

The hardest deployment bugs are silent: every pod is 1/1 Ready, yet the product is subtly broken — a workload missing, a TLS certificate still provisioning, a backend wired to ephemeral storage. Liveness does not equal correctness.

So the definition of "done" is an executable checklist, not a page to tick through by hand. A deployment is complete only when a single status command is green across every dimension:

presence
Workloads & expected components
Every desired replica Ready — and every expected component present, so a disabled or missing service is flagged, not silently absent.
deps
App dependency health
Each service's /ready probe confirms its real backends (Postgres, OpenSearch, OpenFGA, object storage) — not just that the pod started.
edge
TLS certificates Active
Managed certificates must be Active, not provisioning — a 1/1 pod behind a half-issued cert is unreachable over HTTPS.
correctness
Config & schema correctness
The semantic checks liveness can't see: durable (not ephemeral) conversation storage, the analytics/KPI store wired, runtime catalog sources reachable, DB migrations applied.
Green means the site works end to end — not "the pods are up". Treat the status command as the source of truth: if a written step ever disagrees with it, trust the command.

What runs in the cluster

A Fred instance lives in one Kubernetes namespace. The application services share one Postgres database and an in-cluster OpenSearch; all external traffic enters through a single Ingress. (Full topology and data flows: the Architecture page.)

app
control-plane-backend
Sessions, teams, lifecycle, the admin/analytics surface, and runtime-catalog routing.
app
knowledge-flow (backend + worker)
Document ingestion, vector/tabular stores, and the MCP filesystem. The Temporal worker drains the ingestion queue.
app
fred-agents
The agent runtime. Conversation state (history + checkpoints) persists to Postgres so it survives restarts.
app
fred-frontend
The web UI. Proxies to the backends, so it is brought up last, after their Services exist.
infra
Keycloak · OpenFGA · Temporal (+ UI)
Identity (OIDC + M2M), relationship-based authorization, and workflow scheduling.
data
PostgreSQL · OpenSearch
Relational store (one DB, per-component tables) and the vector / KPI store. Object storage is native GCS via Workload Identity.

Deployment flow

The reference deployment is a Helm chart plus a small set of scripts. The shape:

  1. Build the component images at one shared, date-stamped tag (so a round is one coherent version).
  2. Preflight — verify identity prerequisites (realm, clients, roles) and that all required secrets render.
  3. Deploy in order — migrate the stateful backends, start them, then the agent runtime, and the frontend last (it resolves backend DNS at startup).
  4. Verify — run the status command until it is fully green (the checklist above). Re-run after any change.
Fast iteration. Routine redeploys reuse a one-line image tag and skip re-provisioning identity, so an app-only roll-forward is quick. Bouncing a pod to pick up a config change is a plain rollout restart — no full release needed.

Operational gotchas worth knowing

Hard-won, and transferable to any GKE deployment:

Durable conversation storage. The agent runtime must persist to a real database, not a pod-local SQLite file on an emptyDir — otherwise conversations vanish on every restart while still appearing in the session list.
Analytics needs its store wired. The KPI dashboard reads from OpenSearch; if that sink is not enabled and connected, preset endpoints return 503 even though everything else is healthy.
Don't tear down the edge to "restart". Disabling the frontend deletes its managed TLS certificate; bringing it back triggers a fresh 15–60 min certificate re-provision. Roll the pod instead.
Provisioning isn't free per deploy. Re-running identity provisioning on every upgrade is slow; once the realm and clients exist, skip it for app-only redeploys.
